# Internationalization (PL / EN) — design

## Goal

Translate the app into Polish and English and let users switch the language in Settings. Polish stays the default. This supersedes the earlier "Polish only, no i18n library" decision from the UX polish spec.

## Decisions (made with the user)

- Library: `next-intl` (v4, App Router, no URL prefixes, cookie-based locale).
- Preference storage: cookie `NEXT_LOCALE` plus nullable column `User.locale`.
- First visit language: from `Accept-Language` (Polish → `pl`, anything else → `en`, no header → `pl`).

## Locale resolution

`resolveLocale({ userLocale, cookie, acceptLanguage })` in `i18n/locale.ts` (pure, unit-tested). Order: `User.locale` (signed-in, set) → cookie → `Accept-Language` → default `pl`. Invalid values are ignored. `LOCALES = ["pl", "en"] as const`, `DEFAULT_LOCALE = "pl"`.

`i18n/request.ts` (next-intl `getRequestConfig`) reads the cookie and `Accept-Language`, and for a signed-in Clerk user does one `select { locale }` on `User` by `clerkUserId` (wrapped in React `cache`; `// ponytail:` comment — move into the session object if it ever shows in profiles). It returns `{ locale, messages }`.

`<html lang={locale}>`; URLs have no locale prefix.

## Switching

`actions/locale.ts` → `setLocaleAction(locale)`: validates with `isLocale`; sets cookie `NEXT_LOCALE` (1 year, `path=/`, `sameSite=lax`); if a Clerk user is signed in, `user.updateMany({ where: { clerkUserId }, data: { locale } })`; `revalidatePath("/", "layout")`; returns `{ success, message }`. The Settings language select (replacing the current mock state) lists "Polski" and "English" (each in its own language), calls the action, then `router.refresh()`. Settings stays reachable signed-out (cookie only).

## Messages

- `messages/pl.json`, `messages/en.json`, same keys. Namespaces: `common`, `nav`, `system`, `dashboard`, `packages`, `reports` (includes `categories.<key>.{label,suggestions}`, `type`, `status`), `posts`, `admin` (includes `role`), `settings`, `locations`, `auth`, `errors`, `meta` (page titles).
- Types: `global.d.ts` declares `AppConfig { Messages: typeof pl; Locale: "pl" | "en" }` so keys are checked at compile time.
- Plurals via ICU (`{count, plural, one {# paczka} few {# paczki} many {# paczek} other {# paczki}}`; English `one`/`other`).
- Parity test (`i18n/messages.test.ts`): same key set in both files, no empty strings, identical ICU placeholder names per key, arrays of equal length.

## What gets translated

All user-visible text under `app/`, `components/` (except `components/ui` primitives that have none), and server action messages. Specifically:

- navigation, TopBar, system screens (404, error, 403, waiting), empty states, loading `sr-only` text, dashboard.
- packages and reports UI, the category catalog (`catalog.ts` keeps `key`, `visibility`, `types`, `subject`; labels and suggestions come from messages), type/status/role labels (`TYPE_LABEL`, `STATUS_LABEL`, `ROLE_LABEL` replaced by message keys).
- posts, admin, locations (facility names/descriptions move into messages), settings, sign-in/sign-up pages, all `generateMetadata`/`metadata.title`.
- dates and numbers via next-intl formatters (`useFormatter` / `getFormatter`) instead of fixed `dd.MM.yyyy`; Clerk components via `@clerk/localizations` (`plPL`, `enUS`) on `ClerkProvider`.
- server actions use `getTranslations("errors")` / feature namespaces for returned messages.

Not translated: domain/internal exception messages, database values and enums, console logs, webhook responses, user-generated content (posts, report titles and descriptions).

`app/global-error.tsx` renders outside the layout and providers, so it shows a fixed bilingual text ("Coś poszło nie tak / Something went wrong") instead of using next-intl.

## Out of scope

URL locale prefixes, more than two languages (adding one = new messages file + entry in `LOCALES`), RTL, translating user content, language-specific e-mails (the stored `User.locale` makes them possible later).

## Data

`User.locale String?` (null = no choice made). Migration `add_user_locale`; apply to Cloud SQL manually with `npm run db:migrate:gcp`.

## Testing

- `resolveLocale` unit tests (precedence, invalid values, Accept-Language parsing).
- message parity test.
- `npx tsc --noEmit` (typed keys), `npm run lint`, `npm test`, `next build`.
- Browser (no login): `/this-does-not-exist` and the signed-out home render in PL by default and in EN after setting the cookie (`NEXT_LOCALE=en`) or `Accept-Language: en`.
- A grep for leftover hard-coded Polish letters in `app/` and `components/` (outside messages) comes back empty except for allowed exceptions (global-error fallback).
